# human-writing PRD

## 背景

仓库里的 PRD、TRD、用户手册、发布说明和其他正式文档主要由不同 specialist Skill
生成。现有 Skill 能约束事实、流程、章节和交付路径，但没有一套共享规则负责判断
“这段话最终是写给谁看的”。结果是文档容易泄露 Agent 的执行口径，把内部检查、证据
收集和页面操作规范直接写进正文，句子虽正确，却不像真实读者会读到的说明。

原始 `human-writing` 项目提出了三个可复用的原则：内容必须有材料支撑，每一段都要推进，
中文应先交代主语和动作。它面向论坛、博客和创作长文的部分硬禁令不适合直接套到技术
文档。本功能吸收其方法，不复制其文体。

在 LLM Wiki 文档站优化案例中，`human-writing` 成功帮助整站删除 Agent 话术、报告腔和
机械表达，同时暴露出现行契约的三处不足：第一轮容易只做事实纠偏和句子改写，不主动
判断章节分类是否符合读者任务；"preserve structure" 容易被理解成保留现有布局而不是
主 Skill 规定的必要结构；"只修改命中段落"让整站任务停留在局部润色。此外，契约只覆盖
读者视角、信息顺序、段落和句子，没有描述作者还要做的内容取舍、重点安排和多文档组织，
也缺少高风险事实回传主 Skill 核验的明确动作。

## 当前状态与目标状态

| 维度 | 当前状态 | 目标状态 |
| --- | --- | --- |
| 文档事实 | 各生成 Skill 分别维护 | 继续由主 Skill 独占，`human-writing` 不改事实 |
| 写作对象 | 常从 Agent 执行流程出发 | 先判断真实读者、阅读目的和下一步动作 |
| 组合关系 | PM 入口已能共同加载，下游直接调用仍可能遗漏 | 六个下游 Router 与三十二个 Specialist 都具备按需共同加载条件 |
| 输入方式 | 容易要求用户补齐固定字段 | 从自然语言、主 Skill 和相邻文档推断；只有关键歧义才追问 |
| 改稿方式 | 容易全篇重写或换同义词 | 保留有效内容，只修正读者视角、组织和表达问题 |
| 工作范围 | 只区分新建与改稿，改稿默认只动命中段落 | 写前判断创建、改写或审查，并识别句子、单篇、文档集合和整站范围，按范围采用相应工作方式 |
| 作者决策 | 契约只覆盖读者视角、信息顺序、段落和句子 | 覆盖内容取舍、文档信息组织、重点详略和解释方式 |
| 结构权限 | "保留结构"容易被读成保留现有布局 | 明确保留主 Skill 规定的必要结构与真实流程；授权后可调整现有分组和归类 |
| 高风险事实 | 要求保留但缺少疑问时的动作 | 权限、数据边界、自动行为等存在疑问时停止润色，返回主 Skill 核验 |

## 产品目标

1. 提供一个独立的 `human-writing` Skill，为所有面向真实读者的文档生成与更新提供共享写作规则。
2. 让 Agent 从用户请求、主 Skill、目标文件和相邻文档中推断读者、任务、文种和语气，不要求固定输入表单。
3. 保持主 Skill 的事实、操作顺序、术语、格式和安全边界不变，只改善组织与表达。
4. 删除正文中的 Agent 内部执行口径，让每一段为读者增加事实、动作、结果、限制或解释。
5. 支持直接调用，也支持由 Router 或文档生成类 Skill 动态共同加载，不形成消费链或后处理流水线。
6. 让 PM handoff 路径与直接 slash 调用使用同一触发条件，避免绕过 Router 时写作能力下降。
7. 明确 `human-writing` 是读者型文档的编写实现层，覆盖创建、改写和审查，从文档开始编写时就参与内容选择和组织。
8. 写作前判断修改范围（句子、单篇、文档集合、文档站），按范围采用相应工作方式；局部任务不做全站盘点，整站任务不缩减成局部润色。
9. 将"有人味"落实为对读者、内容取舍、信息组织、重点和解释方式的主动判断，不只覆盖句子。
10. 明确保留的是主 Skill 规定的必要结构与真实流程，而不是无条件保留现有信息布局；在用户或主 Skill 授权范围内可以调整文档信息架构。
11. 遇到权限、数据边界、自动行为等高风险事实疑问时，返回主 Skill 核验，不把不确定描述润色成确定事实。

## 非目标

- 不替代 PRD、TRD、manual、API、ops、QA、Release Notes 等主 Skill。
- 不为文档虚构产品能力、操作步骤、用户经历、数据、引语或案例。
- 不建立作者画像、品牌语气配置中心、模板引擎或长期记忆。
- 不在首版增加机械禁词脚本、评分服务、运行时依赖或新的共享目录机制。
- 不因某个 Skill 会写文件就强制加载；纯代码、配置、schema、lockfile 和数据输出不触发。
- 不新增独立的文档架构或网站架构 Skill；整站优化只是多文档写作模式的一种应用。
- 不接管产品 UX 信息架构、网站导航实现或正式文档 owner；文档信息架构只作用于目标文档及其文档集合。
- 不要求局部文字修改也扫描整个仓库；未获用户或主 Skill 授权时不移动、拆分或合并文件。
- 不恢复已移除的 Skill eval 体系、模型评分或 prose lint 机制，验收继续依赖真实项目案例和人工语义验收。

## 用户与场景

| 用户 | 场景 | 期望结果 |
| --- | --- | --- |
| 文档读者 | 阅读用户手册、产品说明或发布说明 | 快速知道能做什么、怎么做、会看到什么 |
| 研发协作者 | 阅读 PRD、TRD、API、运维或 QA 文档 | 找到决策、约束、接口、验证和风险，不读重复套话 |

| Skill 维护者 | 为文档生成能力接入统一写作规则 | 保留主 Skill 权限和交付契约，不复制规则 |

## 规则优先级

```mermaid
flowchart LR
    U["用户明确要求"] --> P["主 Skill 的事实、流程、安全、结构和格式"]
    P --> H["human-writing 的读者视角、组织和表达"]
    H --> O["同一份面向目标读者的文档"]
```

发生冲突时，`human-writing` 必须退让于更高优先级规则。它可以重排解释顺序，不能重排
真实操作顺序；可以把抽象名词改成动作，不能改动术语或字段名；可以删除 Agent 的内部
过程说明，不能删除读者完成任务所需的前提、警告和恢复步骤。

## 验收标准

1. `human-writing` 能以独立 Skill 被发现和直接调用，并被归入 PM 插件发布。
2. Skill 规则明确支持与任一文档生成主 Skill 同轮组合，且不接管主 Skill 的事实或交付契约。
3. 输入说明不要求固定表单，能从自然语言和仓库上下文推断写作条件。
4. 使用手册样例中不再出现 Agent 截图规范、内部检查口径或“确认索引已加载”式验证动作，仍保留真实页面操作和可见结果。
5. 技术文档样例保留术语、字段、命令、表格和必要章节，不因“活人感”被改成口语文章。
6. 改稿样例只修改有问题的段落，不制造新事实，不附加写作过程报告。
7. Skill、注册、README、lock 和仓库检查保持一致。
8. 六个下游 Router 和三十二个 Specialist 均能检索到 `human-writing` 共同加载条款，`pm-agent` 保留上一批实现。
9. 纯代码、配置、schema、lockfile 或数据输出不会仅因 Skill 被直接调用而加载写作能力。
10. Skill 明确支持创建、改写和审查三种工作方式，不被描述为后处理润色。
11. Skill 能判断局部、单篇、多篇和整站范围；局部改稿不被迫整站盘点，整站优化不停留在局部措辞替换。
12. "保留结构"在 Skill 本体与所有共同加载条款中统一指必要结构和真实流程，不等于保留现有布局。
13. 结构调整必须获得用户或主 Skill 授权，并交回主 Skill 完成链接、构建和渲染验证。
14. 高风险事实存在疑问时返回主 Skill 核验，不输出更肯定的改写。
15. 不增加 prose lint、模型评分或 Skill eval 体系；使用 LLM Wiki 整站案例完成一次人工语义验收。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 把“活人感”误解为口语化 | 技术文档失真或不专业 | 明确活人感来自读者位置、材料和推进，不来自俚语、错字或假经历 |
| 写作规则覆盖主 Skill | 操作顺序、格式或安全提示被改坏 | 固定规则优先级和事实保护清单 |
| 规则过多导致输入僵化 | 用户必须先填写模板 | 默认推断，只有实质歧义才追问 |
| 机械禁词产生误伤 | API、表格和说明文表达受限 | 首版使用语义判断，不增加全局标点禁令或 lint 脚本 |
| 所有文档一套口吻 | 文种差异消失 | 按文种读取最小参考文件并保留主 Skill 的结构 |
| 能力扩张后接管主 Skill | 事实、路径或验证归属混乱 | 固定主 Skill 对事实、必要结构、路径和验证的所有权，结构性修改交回主 Skill 验证 |
| 与 Designer 的信息架构职责冲突 | 角色边界模糊 | 文档信息架构只作用于目标文档及其文档集合，不接管产品 UX 信息架构 |
| 每次改稿都扫描全站 | 局部任务成本膨胀 | 先判断修改范围，按最小充分范围工作 |
| 未授权移动文件 | 文档组织被破坏 | 结构修改必须由用户或主 Skill 明确允许 |
| 为"有人味"牺牲事实 | 高风险描述失真 | 权限、数据边界、自动行为等疑问回传主 Skill 核验 |
| 形成新的机械检查表 | 语义判断被字面扫描替代 | 所有检查按语义和文种判断，不引入禁词脚本或评分 |

## 开放问题

当前无阻塞开放问题。跨插件 Skill 通过已注册名称 `human-writing` 共同加载，不建立会逃出
插件复制边界的相对路径引用。
